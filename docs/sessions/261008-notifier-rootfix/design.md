# DESIGN-note：通知内容有界且凭据不进入诊断输出

## 目标

修复 #1/#2/#3：调用方继续使用原有发送 API，长内容由库完整分段；正常日志与错误信息不泄露 webhook 凭据。多请求不承诺原子送达，全部分段被接口接受才成功，任何失败必须明确可见。

用户已批准根治方向，并明确选择「内容优先，允许降级」：不可容纳的单个链接/表格行允许按文本切分；不删正文，不隐瞒格式代价。代码块补围栏且保持正文缩进/换行。

## 非目标

不替下游预切；不新增重试、fallback 链、后台线程、配置框架、公开 API 或依赖；不替另一个会话整理旧测试/接入 CI；不改生产、不轮换真实密钥、不发布 PyPI。准备补丁版本与构建不等于对外发布。

## 为什么不是分区 / 删除 / 约定

- **分区**：平台有不同协议与限制，但两平台都会读取同一分段器，凭据也进入多个日志位置；仅分文件不能保证输出。
- **删除**：删长消息能力会违反库自动分段用途；停日志会丢诊断能力。删除原始 URL/原始异常的诊断输出，保留非敏感身份和安全错误信息。
- **约定**：靠开发者每次记得预留页码或截断 URL 已失败。需要现有生产出口统一控制，但不新建通用框架。

## 方案要点与已否决方案

- **要点**：
  1. A 卡处理 #1：诊断身份与授权 URL 分离；企微/飞书、单 webhook/池、正常/失败日志与公开错误均覆盖。少量共用函数有两平台真实消费者。
  2. B 卡处理 #2/#3：复用并收敛现有分段器的产出规则，最终内容经过页码、围栏和审核修改后仍有界。interactive 正文采用 Markdown 分段，标题分页明确。
  3. 默认保正文而非无限格式承诺：普通链接/表格/代码保持结构；超大不可分元素采用固定文本规则，并文档明确。测试保留正文缩进/换行，不全局忽略空白。
  4. 平台计量先核一手文档；正文上限量解析后字段，若整请求上限存在则量 requests 实际 prepared body。不能将自造 JSON 重编码当作线上字节。
  5. 审核替换可能扩张正文，最终计划必须受预算控制。默认不改变现有审核策略/触发范围；若确需前移审核，列真实语义差异并上报后再做。
  6. 发送前检查用于阻止不合规计划，而非取代分段。应在首次网络请求前发现本地可判定的非法分段；网络中途失败允许已有部分送出，但不得成功。
  7. A/B 有 sender/manager/pool/飞书文件交集，默认 A 合并后 B 基于最新主干实施。外部测试整理卡与 A 并行，A 仅新增自有回归文件，不动它持有的旧测试/Makefile/AGENTS。
- **已否决**：仅补三处边界分支；只加拒发；URL 字符截断脱敏；靠关闭日志或吞错；未经规范依据改 JSON 编码；全局忽略空白验完整；只数围栏偶数；固定 20 字节预留宣称无限分页；让下游重复预切。

## 关键不变式

这些是目标约束，未实现/未验证之前不宣称达成。

1. 凭据不进入本库主动发布的日志或 SendResult.error；实例可区分。实现：core 的小型凭据/身份函数及各平台日志/异常位置。锁定：tests/test_webhook_credentials.py，真实 loguru DEBUG sink、两个不同假 key、API/网络/worker/池异常。异常记录须避免经用户自配 sink 重新带出原始凭据。
2. 每段最终正文满足对应平台/类型预算，包括页码、围栏、审核替换。实现：core/segmenter.py、manager/pool/feishu 发送计划及 sender 最终检查。锁定：tests/test_bounded_delivery.py，真实 public notifier → requests 传输边界，表格/长行/代码/interactive/审核扩张/池路径。
3. 原始正文或按既有审核策略变换后的正文完整；只允许规则列明的额外页码、重复表头、补围栏及分页呈现。实现：分段器。锁定：含唯一行号、中文/emoji、连续换行、代码缩进的 fixture；移除明确插入项后按已定义规则重建。不可全局删空白。
4. 非法发送计划在首次 POST 前失败；远端任一分段失败则 SendResult 非成功。实现：已有发送路径失败状态。锁定：零请求断言与「第一段成功、第二段 API/网络失败」状态断言。
5. 公共方法签名兼容；无需调用方自行分段。实现：平台 notifier API 不变。锁定：既有向后兼容测试及上述入口回归。

## 待验证前提

1. [推断] 飞书 19000 为当前项目正文预算；官方整请求/正文限制和签名/标题开销口径需 B 卡核验并持久化文档出处，不能引用常量注释自证。
2. [推断] 企微 text 与 markdown_v2 可能限额不同，按真实官方文档确定，不沿用统一 3800 假设。
3. [推断] 真实 loguru 异常堆栈会泄露局部 URL；A 卡须实际制造异常并捕获用户自配 sink 验证，不只改 setup_logger。
4. 测试整理和 CI 接入由另一会话负责；本批依赖其主干产物进行最终全量/门禁验收，不接管其 PR 或修改其在途文件。

## 验收路径

1. A：本地真实 loguru 配置 → 两平台 public send_text/send_card/send_markdown 与池 → 模拟远端成功/网络/API/worker 失败 → 捕获日志和 SendResult，假密钥零泄露且实例可识别。
2. B：5KB+链接行、10KB+表格单元格、标题相邻10KB+代码块、30KB+中文卡片、审核扩张 → 实际 public API → 截获 requests 最终请求；逐段检查正确计量对象、正文、标题、页码和失败状态。
3. 新测试在原基线应因目标断言失败而转红；修复后目标文件及全量 make test（外部测试卡落地后）通过。
4. 每张实现卡：draft PR → 本地测试与独立审查 → ready → 实際 CI/gate 项目核对 → 全绿合并。若 CI 尚未接入，明确为无门禁，不能冒充绿或擅自写默认分支。
5. A/B 合并后准备0.3.2、变更说明、构建轮子及隔离安装验证；对外发布/下游生产升级另需明确授权。
